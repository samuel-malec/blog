    Diplomka proposal

    This document serves as a brief introduction into the concepts this project is concerned with, while also serving as my personal notes.

    Motivation

    Whole-program inter-procedural analyses are difficult to implement efficiently. This is simply due to the sheer scope on which the analyses operate. Modern compilers therefore rely on local analyses combined with function summaries that approximate the behaviour of callees. That is the reason why we are trying to find a way that would make inter-procedural analyses slightly easier to reason about.

    Essentially, we would like to find a suitable way to extract and represent side-effect information of functions. If we would be able to do that, in theory we could create comprehensive function summaries based on the discovered side-effect information and utilize these summaries for exeample in an simple abstract interpretation analysis within an existing AOT compiler infrastructure.

    Graal IR Basics

    Graal IR is a sea-of-nodes (SoN) representation used by GraalVM compiler. It contains a large amount of nodes. Each node roughly corresponds to a high level instruction such as arithmetic, memory access, or a call.

    Nodes are roughly divided into two kinds:

    • Fixed nodes are pinned to a specific point in the control-flow order. They are connected to their neighbours via successor edges. Invoke, If, Return, and any node with side effects are typically fixed.
    • Floating nodes are constrained only by their data dependencies (input edges), not by any fixed position in control flow. The scheduler is free to place them wherever their inputs are available and their outputs are needed, e.g. an AddNode with no side effects can float to whichever block is most profitable (such as being hoisted out of a loop).

    It is worthy mentioning that the more nodes that can be classified as floating rather than fixed, the more freedom the scheduler and later optimization passes have (well at-least this was the raison-d'entre for SoN). Invoke nodes are fixed by default which is one of the two reasons calls end up serialized relative to each other (see "Why Calls Get Serialized" below for the other).

    To demonstrate Graal IR, suppose this Java program:

    public class Fibonacci {
    public static int rec(int n, int a, int b) {
        if (n == 0) {
            return a;
        }

        return rec(n - 1, b, a + b);
    }

    public static int fib(int n) {
        return rec(n, 0, 1);
    }

    public static void main(String[] args) {
        System.out.println(fib(5));
    }
}

    The Graal IR of the Fibonacci::rec method is depicted below. The control edges are marked in red, whereas the data edges are marked in blue or black. There is a unique Start node, from which the control flows. The Begin nodes roughly correspond to the beginning of a basic block. One may find it strange that there are two control edges flowing from the Invoke!#Fibonacci.rec node — this is because Fibonacci.rec is a recursive function, and Graal IR puts a stack-overflow check into the IR, giving two paths from this node: one for normal return, and one for the exception path taken if a StackOverflowError is thrown, in which case we unwind.

    The Invoke!#Fibonacci.rec node above is a concrete instance of a fixed node in the sense described earlier: it sits directly in the successor chain, which is exactly what forces the normal-return and exception paths to be modeled as explicit control edges rather than left floating.

    To quickly find more detailed examples of Graal IR, I recommend looking at this nice blog post.

    Graal Memory Model

    Graal tracks memory side effects coarsely using a concept called LocationIdentity. Every node that can write to memory implements either SingleMemoryKill (kills exactly one identity, exposed via getKilledLocationIdentity()) or MultiMemoryKill (kills several, via getKilledLocationIdentities()). Every node that reads from memory implements MemoryAccess and exposes the identity it depends on via getLocationIdentity(), plus a pointer to the last node that could have killed that identity via getLastLocationAccess()/setLastLocationAccess().

    LocationIdentity forms a small lattice:

    • LocationIdentity.any() — the top element; conflicts with everything.
    • NamedLocationIdentity — a named "family" of locations, e.g. all int[] elements, or a hand-picked identity for a class of internal VM fields.
    • FieldLocationIdentity — one identity per declared field, shared across all instances of that field (i.e. still not per-object, but already narrower than any()).

    A memory operation's ordering relative to another is decided purely by whether their identities overlap: two operations with provably disjoint identities may be reordered or interleaved freely; two operations that share (or might share) an identity must stay ordered.

    The crucial default: an ordinary Java method call (InvokeNode) has no interprocedural information available to the compiler about what it touches, so it is constructed with identity = LocationIdentity.any(). This makes every call a SingleMemoryKill on any(), i.e. a full memory barrier. In the example below, bump(counter)'s write and config.limit's read — despite obviously touching disjoint objects — are therefore always ordered relative to each other in the graph, and neither the scheduler nor floating-read/read-elimination passes are allowed to reorder or interleave memory operations around them.

    This is a deliberate conservative default: nothing in the Graal compiler currently computes narrower, points-to-informed LocationIdentity values for general method calls. That gap is exactly what this project investigates.

    class Counter { int value; }
class Config { int limit; }

static void bump(Counter counter) {
    counter.value++;
}

static void process(Counter counter, Config config, int n) {
    for (int i = 0; i < n; i++) {
        bump(counter);
        if (i > config.limit) {
            break;
        }
    }
}

    Semantically, bump(counter) and the read of config.limit are independent of each other because they touch (read from/write to) different objects. Unless the compiler can prove this fact, both instructions are conservatively assumed to affect the same heap state, so Graal introduces a dependency between them. This is very costly, because inside because the process method config.limit never changes across loop iterations, so the read is loop-invariant and should ideally be hoisted out of the loop.But because it's forced to depend on bump's any() memory kill, it stays pinned inside the loop body.

    It might seem like the natural fix is to somehow make the Invoke node floating, but this is not what we are proposing, and it isn't possible given how Graal's node hierarchy is structured:

    • FloatingNode is defined with no successor edges at all: it is a plain ValueNode, structurally incapable of having a control-flow successor. InvokeNode (and InvokeWithExceptionNode), by contrast, extend FixedWithNextNode/have mandatory successor edges — a normal-return path, and for InvokeWithExceptionNode, an exception path as well. A call also carries a FrameState for deoptimization, which must correspond to a specific program point. None of this fits the floating-node contract.
    • There is no FloatingInvokeNode in Graal, and there structurally cannot be one in the current node model: "floating" means no fixed control position, which is semantically wrong for an operation that can throw, deoptimize, or otherwise be observed as happening at a specific point relative to other side effects.

    What Graal does already support is promoting memory accesses (not calls) from fixed to floating form. This is the actual mechanism we want to reuse/extend:

    • FloatingAccessNode is the floating counterpart of a fixed memory access (e.g. FloatingReadNode vs. ReadNode). A fixed access such as ReadNode exposes canFloat(), and when it can, asFloatingNode() converts it into the equivalent FloatingAccessNode, dropping its position in the successor chain and replacing it with a data dependency on getLastLocationAccess() instead.
    • FloatingReadPhase is the compiler phase that performs this conversion. Its FloatingReadClosure.processFloatable walks the fixed-node schedule, and for every FloatableAccessNode that can float, looks up the current "last known kill" of its LocationIdentity in a per-location map (MemoryMapImpl), then calls graph.replaceFixedWithFloating(accessNode, floatingNode). Crucially, every SingleMemoryKill/MultiMemoryKill node it walks past — including every InvokeNode, since it kills any() by default — updates (or, in the any() case, clears) this map, which is exactly what pins a read like config.limit to stay after bump(counter) in program order.
    • SchedulePhase is the phase that assigns floating nodes to basic blocks once they are floating. It does not decide where fixed nodes go — a fixed node's block is a mechanical consequence of the successor chain it already sits in (see ControlFlowGraph.renumberBlocks), and SchedulePhase explicitly treats a fixed node's earliest and latest legal block as identical, i.e. no freedom at all. What SchedulePhase actually computes is the earliest/latest legal block for each floating node — including newly-floated FloatingReadNodes — based on data dependencies (scheduleEarliestIterative) and, on the latest side, on which blocks are known to "kill" the node's LocationIdentity (fillKillSet/checkKillsBetween). A block containing an invoke that kills any() blocks every floating access from being scheduled past it, regardless of what that access actually touches.

    So the mechanism we intend to use is: narrow the LocationIdentity that InvokeNodes report, not change their fixed/floating status. InvokeNode already has a constructor overload accepting an explicit LocationIdentity instead of defaulting to any(). If a call's kill identity is narrowed based on points-to information (e.g. tagged with a Counter-heap token instead of any()), then:

    • FloatingReadClosure.processAccess/processCheckpoint will only invalidate the map entry for that specific identity, instead of clearing the whole map — config.limit's entry survives across the bump(counter) call.
    • SchedulePhase's kill-set computation no longer treats every block containing bump as killing everything, so the read of config.limit becomes a legal candidate to float, hoist out of the loop, and get scheduled once instead of every iteration.

    No changes to FloatingReadPhase or SchedulePhase themselves are required — both already consume LocationIdentity at the right granularity. The only missing piece is a source of narrower identities for ordinary method calls, which is what the points-to-informed heap-partition analysis in this project aims to provide.

    MemoryAccess represents any node that reads from a memory location. It exposes getLocationIdentity() (which location it reads) and getLastLocationAccess()/setLastLocationAccess() (a pointer to the last node in the memory graph that could have killed that location).

    SingleMemoryKill/MultiMemoryKill represent nodes that write/invalidate one or several LocationIdentitys respectively.

    The SSU angle: the project's proposal is to break this monolithic memory dependency into fine-grained, partitioned linear tokens (e.g. a Counter-heap token and a separate Config-heap token). Disjoint heap regions then get independent data-flow paths, and the false dependency between bump's write and config.limit's read disappears — unblocking the hoist. The same mechanism addresses three related problems at once:

    • Breaking the monolithic memory graph. A single write currently invalidates memory state globally for the local optimizer, because Graal can't cheaply tell whether a read and a write touch different heap regions without deep, expensive alias analysis across the whole graph. Partitioned tokens make disjointness explicit and free.
    • Reducing reliance on aggressive inlining. Industrial compilers lean on inlining small functions (getters/setters) specifically to extend the reach of local optimizations — at the cost of code bloat, worse instruction-cache behaviour, and AOT compile-time overhead. Lightweight interprocedural summaries (input/output side-effect tokens on the function prototype) let Graal optimize a call site without inlining the callee body.
    • Unlocking LICM/CSE/DCE that are currently blocked. Rigid control and memory-ordering edges between operations prevent loop-invariant reads from floating and prevent pure/repeated calls from being deduplicated or removed. Replacing those rigid edges with flexible data-dependency chains lets Graal's existing scheduler reorder and hoist freely.

    Key takeaway: the goal is to turn implicit, coarse-grained memory side effects into explicit, fine-grained data dependencies — letting Graal's existing local optimizer passes (LICM, CSE, DCE) reach their full precision without paying the code-size and compile-time cost of aggressive inlining.
